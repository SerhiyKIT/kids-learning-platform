# Конвенції проєкту

Практичний чекліст для рев'ю, а не есе. Кожен пункт позначено способом перевірки:

- **[CI]** — перевіряється автоматично на кожен push/PR (`.github/workflows/ci.yml`).
- **[test]** — має бути власний тест на кожну нову фічу, що цього торкається; не перевіряється глобально.
- **[review]** — рев'ювер перевіряє очима; автоматичної перевірки немає (або є фундаментальна причина, чому вона неможлива).

Джерела рішень: `docs/Технічний_фундамент.md`, `docs/Ролі_та_приватність.md`. Цей документ їх не дублює, а фіксує, **як саме** ці рішення втілені в коді сьогодні.

## Backend

| Конвенція | Як перевіряється |
|---|---|
| Модульний моноліт, одна БД (`docs/Технічний_фундамент.md` §1) | **[CI]** межі модулів — `ArchUnitConventionsTest.no_cyclic_dependencies_between_packages` (жодних циклів між пакетами `ua.kidlearn.*`). «Одна БД» — інфраструктурне рішення, **[review]** |
| Лише конструкторна ін'єкція, без `@Autowired`-полів | **[CI]** — `ArchUnitConventionsTest.no_field_injection` (тільки `src/main`; тестові класи навмисно виключені — `@Autowired`-поля для `MockMvc`/репозиторіїв у тестах — стандартна ідіома Spring Boot Test, не порушення) |
| `@PreAuthorize` на контролері + перевірка володіння (ownership) у сервісі | **[CI]** частково — `ArchUnitConventionsTest.controllers_must_not_access_repositories_directly` (контролер не може обійти сервіс і піти напряму в репозиторій). Що саме сервіс перевіряє володіння — **[review]**, оскільки ArchUnit не читає бізнес-логіку методу |
| Помилка володіння → **404, не 403** (щоб не підтверджувати існування чужого запису) | **[test]** — окремий тест на кожен ownership-check (див. `ChildControllerTest.parentCannotSeeAnotherParentsChild`, `AssignmentControllerTest` тощо як приклад) |
| Жодних персональних даних батьків у відповідях вчителю/дитині | **[test]** — DTO, що це гарантує, мають явний коментар («Deliberately excludes...», див. `GroupMemberInfo`, `TeacherResultChild`) + тест, що перевіряє відсутність поля у відповіді |
| Flyway керує схемою; `ddl-auto: validate` | **[CI]** неявно — якщо сутність розійшлася зі схемою, застосунок не піднімається і будь-який тест падає одразу |
| Enum-и як `text` + `CHECK` (не Postgres `ENUM`) | **[review]** — дизайн-рішення в міграції, автоматично не перевіряється |
| Каскади — на рівні БД (`ON DELETE CASCADE`/`RESTRICT`/`SET NULL`), не в Java | **[review]** — див. `V2__core_schema.sql`; каскад видалення дитини перевіряється **[test]** (`ChildControllerTest.deletingChildCascadesToAttemptsAndAnswers`) |
| `audit_log` ніколи не каскадується (рядок мусить пережити ціль) | **[review]** — навмисне рішення з коментарем у `V5__audit_log.sql` (`ON DELETE SET NULL`, не `CASCADE`) |
| Побічні ефекти — асинхронно, `AFTER_COMMIT` (лист, аудит-запис) | **[review]** — патерн, див. `AuthMailEventListener`, `AuditEventListener`. Факт запису перевіряється **[test]** з `Awaitility` |
| Зовнішні провайдери (LLM, TTS) — за інтерфейсом, з dev/CI-заглушками, без мережі при старті | **[review]** дизайн інтерфейсу (`LlmProvider`, `TtsProvider`) + **[test]** що стаб повертає очікюване. Відсутність мережевих викликів при старті неявно підтверджує сам факт, що CI взагалі стартує швидко й детерміновано |
| Валідація **до** збереження (scenario JSON Schema + бізнес-правила) | **[test]** — кожен шлях запису сценарію (ручний, AI-конвеєр, dev-seed) має тест на відхилення невалідного JSON |
| Детерміновані тести: інжектований `Clock`, реальний dev-postgres, `Awaitility`, без `Thread.sleep` | **[review]** — практика, без grep-перевірки на `sleep` поки що. `Clock` — див. `ClockConfig`/`RateLimitingTest.testClock` |
| Dev-only код — лише під `@Profile("dev")` | **[test]** — обов'язковий `*ProfileTest` на кожен новий dev-only контролер, що доводить відсутність біна поза профілем `dev` (див. `DevSeedControllerProfileTest`, `DevAuthControllerProfileTest`) |
| Жодних дефолтних/закомічених credentials | **[review]** + структурно: `.env`/`infra/.env` у `.gitignore`, лише `*.env.example` в репозиторії |
| Найменування: `@RestController` → суфікс `Controller`; `@Service` → суфікс `Service` | **[CI]** — `ArchUnitConventionsTest.rest_controllers_are_named_consistently` / `services_are_named_consistently` |
| `config/` і `scenario/` — листові пакети (не залежать від фіча-пакетів) | **[CI]** — `ArchUnitConventionsTest.config_and_scenario_stay_leaves` |

## Frontend

| Конвенція | Як перевіряється |
|---|---|
| Увесь мережевий доступ — лише через `apiFetch` (`src/lib/api.ts`); без сирого `fetch`/`window.fetch` | **[CI]** — `eslint.config.mjs`, правило `no-restricted-syntax` (виняток — сам `src/lib/api.ts`, єдине місце, де `fetch` дозволений) |
| Same-origin через `next.config.ts`-рерайти (`/api/*`, `/login`, `/logout`) | **[review]** — архітектурне рішення, що робить сесійну/CSRF-куку взагалі можливою без CORS-хореографії |
| Жодного браузерного сховища для авторизації (без `localStorage`/`sessionStorage`) | **[CI]** — `eslint.config.mjs`, правила `no-restricted-globals` + `no-restricted-properties` |
| Типізовані DTO (`src/lib/api-types.ts`) точно відображають бекенд-записи (поле-в-поле) | **[review]** — вручну підтримувана відповідність; автоматичної крос-мовної перевірки типів немає (відомий пробіл — див. «Свідомі компроміси») |
| Роутинг за роллю (`me.role`) на `/dashboard` та захищених сторінках | **[review]** — фронтенд поки без тестового фреймворку (у `package.json` немає `test`-скрипта); перевіряється вручну/рев'ю |
| Стан завантаження й помилки на кожному фетчі | **[review]** |
| Dev-only UI — лише під `process.env.NODE_ENV !== "production"` | **[review]**, з ручною перевіркою при потребі: `next build` + grep по `.next/` підтверджує dead-code-elimination (застосовано при рев'ю `/register`, `/play` dev-кнопок) |

## Процес роботи

| Конвенція | Як перевіряється |
|---|---|
| Малі, CI-перевірені інкременти | **[review]** |
| Одна фіча — одна гілка | **[review]** |
| **SCOPE GUARD**: робити те, що попросили, і не більше | **[review]** |
| Людське рев'ю перед мерджем | **[review]** — процес на GitHub (PR) |
| CI зелений (обидві джоби — `backend-test` і `frontend-build`) перед мерджем | **[CI]** — сам факт статусу перевірки; **[review]**, чи налаштований branch protection, що фізично блокує мердж на червоному CI (варто перевірити окремо в налаштуваннях репозиторію, якщо ще не зроблено) |
| STEP 0 у кожному завданні: спершу інвентаризація, зокрема «підтвердити, що залежність резолвиться, перш ніж на неї покладатися» | **[review]** — практика: перш ніж писати реальні ArchUnit-правила, спершу пишеться й запускається тривіальний smoke-тест на самому `archunit-junit5` (і одразу прибирається, якщо все ок) — щоб не сплутати «правило знайшло проблему» з «залежність узагалі не резолвиться» |
| Виправляти корінь проблеми, ніколи не маскувати (`eslint-disable`, слабший рул, обхід) | **[review]** — приклад цього самого коміту: знайдений цикл пакетів `config↔ratelimit` виправлено переносом класу, а не послабленням ArchUnit-правила |

## Нотатка про межі ArchUnit

ArchUnit перевіряє **структуру** (хто на кого посилається, як названо, чи є цикли), не **поведінку**. Тому «помилка володіння → 404» і «жодних PII батьків у відповіді» — свідомо залишені як `[test]`, а не `[CI]`: щоб перевірити, що сервіс справді повертає 404 (а не просто «якось» звертається до репозиторію), або що конкретне поле відсутнє у відповіді, потрібен реальний виклик ендпоінта з реальними даними — це вже сфера MockMvc-тестів, не структурного аналізу коду.
